# 一、项目概述与目标

## 1.1 项目背景及核心研究问题

隧道衬砌长期受到地质条件、结构荷载、地下水和环境变化等因素影响，容易产生裂缝、渗漏水、剥落掉块与泛碱等病害。
传统人工巡检存在劳动强度大、检查效率有限、主观判断差异明显以及微小缺陷难以发现等问题。

本项目拟构建一套以香橙派为硬件核心的智能检测系统，实现：

- 自动识别：识别衬砌表面四类典型病害，输出类别、位置与置信度。
    
- 低光照适应：提升弱光、照明不均匀和局部阴影条件下的检测能力。
    
- 轻量化边缘推理：完成YOLOv8n优化、CANN模型转换和NPU硬件加速。
    
- 病害信息量化：实现病害数量、位置和区域特征统计，并在满足标定条件时估计实际尺寸。
    
- 远程监测：实现数据存储、异常记录、网络上报和网页监控。
    

项目重点研究四个相互关联的问题：

1. 在低光照和复杂纹理背景下，如何提高细小裂缝的检出能力？
    
2. 在昇腾NPU算子兼容性约束下，如何设计兼顾精度、速度和模型复杂度的轻量化检测算法？
    
3. INT8量化对不同病害类别，尤其对细小裂缝检测产生多大影响？如何降低精度损失？
    
4. 如何使算法从离线图像检测真正转化为长时间稳定运行的边缘监测系统？
    

## 1.2 项目研究边界

为确保一年内能够完成，应明确以下范围。

核心范围：

图像采集、四类病害检测、低光照增强、模型轻量化、FP16/INT8部署、NPU推理性能优化、本地病害记录、网络上报和Web监测。

扩展范围：

基于分割的裂缝宽度测量、毫米级尺寸标定、病害严重程度评估、复杂场景下的多摄像头协同。

暂不纳入：

隧道巡检机器人自主导航、全隧道三维重建、结构承载力诊断，以及未经现场标定的高精度病害尺寸测量。

尤其需要注意：原型系统应定位为辅助人工巡检与病害筛查，而非在未经现场验证时直接宣称能够完全替代专业人工检测。

## 1.3 量化目标与验收指标

建议将考核分为基础交付、核心研究目标和挑战性目标。其中基础交付必须实现；研究指标用于指导优化，但不应在尚未实验前认定已经达到。

| 维度       | 建议核心目标                       | 评价方式             |
| -------- | ---------------------------- | ---------------- |
| 数据集规模    | ≥3000张独立原始图像，覆盖4类病害和正常背景     | 数据清单、标注文件、去重报告   |
| 数据质量     | 关键标注抽查合格率≥95%                | 双人复核、标注框或掩码IoU检查 |
| 综合检测精度   | mAP@0.5 ≥0.80                | 固定独立测试集          |
| 微小裂缝检测   | 在约定检测阈值下裂缝Recall ≥0.80       | 独立细小裂缝子集         |
| 算法改进效果   | 裂缝类AP@0.5较Baseline提升≥3个百分点   | 同数据、同训练条件对比      |
| NPU推理性能  | 640×640，batch=1，纯模型推理≥30 FPS | ais_bench与实际推理程序 |
| 端到端性能    | 单路视频流有效检测吞吐≥20 FPS           | 包含采集、增强、推理和后处理   |
| INT8量化损失 | mAP@0.5较同版FP16 OM下降≤2个百分点    | 两种OM模型配对评测       |
| 运行稳定性    | 连续运行≥2小时，无未恢复的程序崩溃           | 性能日志、错误日志        |
| 系统完整性    | 检测、记录、图片存储、远程上报、网页查看全部可用     | 端到端功能测试          |
| 研究成果     | 完成1篇论文初稿及至少1项知识产权申报材料        | 文稿、实验和代码归档       |

注：表中数值为建议验收目标，不是来自官方板卡的实测承诺。mAP、Recall、FPS应在不同数据划分和测试场景下分别报告，不能相互替代。

为保证考核严谨，另外建立以下原则：

- mAP至少同时报告 `mAP@0.5` 与 `mAP@0.5:0.95`，并给出四类病害各自的AP。
    
- 小裂缝除常规AP外，单独统计细窄目标的召回率及误检情况。
    
- FPS区分纯NPU执行速度与完整系统有效处理速度，并提供P50/P95延迟。
    
- 低光照评测使用专门划分的数据子集，不能只报告综合平均精度。
    
- 若不能获得可靠的物理尺度标定，只交付像素级病害量化结果，不将其称为毫米级测量。
    

## 1.4 总体预期成果

R1：隧道衬砌病害数据集

数据说明文档、数据清洗与标注规范、训练/验证/测试划分、四类病害统计信息。

R2：昇腾NPU轻量化检测模型

R3：边缘检测原型系统

支持实时视频检测、病害记录、状态监控、远程数据访问和断网缓存的可演示系统。

R4：论文及知识产权成果

完成论文初稿、关键实验数据、专利技术交底书或软件著作权申请材料。

| C：系统负责人    | 视频采集、推理调度、后端、数据库、远程监控                | Python、Flask/FastAPI、多线程、SQLite、HTTP、基础前端     | 系统功能、远程监控和工程交付   |

|项目阶段|主导人|其他成员参与方式|

|基础环境与部署验证|B|A提供预训练模型，C协助摄像头与Demo|

核心管理原则：每项交付物必须有唯一负责人，但关键环节必须由另一名成员复核。

例如，A训练的模型只有在B完成ONNX检查和至少一次ATC试转换之后，才可以列入最终候选模型。

## 2.3 协作与进度管理

建议团队每人每周投入约8—12小时，在训练、联调和验收集中期适当增加。

具体机制如下：

1. 每周一：15分钟工作会议。 三人分别说明上周成果、本周任务和当前阻塞问题。
    
2. 每周六：2—3小时集中协作。 安排标注复核、代码评审、硬件调试和系统联调。
    
3. 每两周：一次导师汇报。 重点提交可验证成果，不以学习时间、代码行数衡量进度。
    
4. 每月末：一次正式里程碑验收。 保留测试数据、日志、截图和提交记录。
    
5. 每阶段末：一次交叉技术验收。 A验证精度，B验证部署，C验证接口和运行稳定性。
    

建议使用Git进行代码管理，项目管理使用GitHub Issues、飞书或其他团队统一工具。训练数据和模型权重使用独立存储，不将大体积数据文件直接提交普通Git仓库。

每项任务的完成定义为：代码或数据已提交、相关说明已编写、验收测试已通过、其他成员可以复现。

# 四、技术路线详述

## 4.1 总体系统架构

建议采用“离线训练 + 边缘推理 + 远程管理”的三层架构。

离线训练与模型开发层（PC / GPU）

数据清洗与标注 → YOLOv8n训练 → 算法优化 → ONNX导出 → AMCT量化 → ATC编译

边缘检测层（Orange Pi AIpro）

摄像头采集与帧缓存

自适应图像增强

NPU / OM模型推理

解码、NMS与缺陷定位

病害统计与量化

SQLite本地缓存

远程监控层（PC服务器 / 可选云服务器）

HTTP数据上报 → 后端接口 → 病害记录查询 → 统计分析 → Web可视化

这套架构将模型训练放在PC或GPU服务器，香橙派主要负责推理，避免将开发板有限的CPU及内存资源用于复杂网络训练。

## 4.2 数据工程

主导：A　参与：B、C　实施时间：第2—4个月

### 4.2.1 数据来源与样本组成

建议数据集采用“公开数据 + 自主采集 + 训练增强”的方式构建。

已核实的公开资源包括 [TACK Tunnel Data（TTD）](https://github.com/weiliuan/TACK_Tunnel_Data)。该数据集来自三条隧道，具有裂缝、水渗入和析出物三类缺陷标注，并提供分割掩码。项目说明中的785张裂缝、197张水渗入、316张析出物图像与其公开介绍一致。它不直接提供完整的四类目标体系，尤其缺少剥落掉块类，需要另行补充。

推荐建立以下数据结构：

| 类别     | 标签              | 建议独立正样本量 | 特别关注            |
| ------ | --------------- | -------- | --------------- |
| 裂缝     | `crack`         | ≥900张    | 细窄裂缝、网状裂缝、阴影干扰  |
| 渗漏水    | `leakage`       | ≥400张    | 潮湿区域、深色水迹、局部反光  |
| 剥落掉块   | `spall`         | ≥300张    | 混凝土剥落、露骨料、掉块边缘  |
| 泛碱/析出物 | `efflorescence` | ≥300张    | 白色析出物、墙面污渍混淆    |
| 正常背景   | 无缺陷框            | ≥600张    | 衬砌接缝、施工痕迹、管线、阴影 |

上述为建议采集配额，不代表公开数据现有数量。图像可含多个类别，类别计数允许重叠。最终数据集总量按去重后的独立原始图像计算，人工增强图像不计入3000张目标。

如果剥落和泛碱样本在第3个月末仍不足，优先采用导师合作渠道、合法公开数据或实验室模拟拍摄补充，不宜用大量生成图片直接代替真实测试样本。

### 4.2.2 统一标注规范

推荐使用CVAT或Labelme管理需要分割的样本，YOLO格式用于最终检测模型训练。

操作流程：

1. 先抽取每类50—100张图像进行试标注。
    
2. 由A编写《病害标注规范v1.0》，明确四类判别标准与边界情况。
    
3. 三人交叉标注同一批样本，记录意见分歧。
    
4. 对不明确的病害类型标记为待复核，不强行归类。
    
5. 统一转换为YOLO格式，并进行自动格式校验。
    
6. 对全部标注抽样检查，对细小裂缝及类别交界样本进行重点复核。
    

建议同时建立每张图像的元数据：

```
image_id
source_dataset
tunnel_id
capture_time
lighting_condition
camera_id
image_width
image_height
defect_labels
annotation_status
```

标注一致性不建议仅依赖Kappa系数，因为目标检测还涉及目标位置和边界。应同时检查类别一致率、匹配目标的IoU及漏标率。

### 4.2.3 训练、验证与测试划分

建议初步采用：

|子集|比例|用途|
|---|---|---|
|Train|70%|模型训练与数据增强|
|Validation|15%|超参数选择、阈值调节、模型筛选|
|Test|15%|最终独立性能验证|

比例只是初步目标。优先保证隧道来源或连续视频场景之间不发生泄漏，而非机械追求图像数量严格等于7:1.5:1。

建议以 `tunnel_id + capture_session` 为分组单元。同一个场景的连续帧、重复裁剪图像和由同一原图生成的增强结果不能横跨不同子集。

另外预留跨隧道独立测试子集，用于评估模型迁移到新隧道的表现。如果来源隧道数量不足，应明确报告无法充分验证跨场景泛化的局限。

量化校准集从训练集单独抽取200—400张具有代表性的图像，覆盖不同类别、正常光照、弱光、过曝和复杂背景。验证集可以用于量化策略选择，最终测试集不得用于选择量化参数。

### 4.2.4 数据质量检查

第4个月之前必须运行数据检查脚本，至少实现：

- 检查缺失文件、无效路径、损坏图片、异常标注坐标。
    
- 检查同一图像内的重复框和明显错误框。
    
- 使用图片哈希或感知哈希辅助发现重复图像。
    
- 统计各类别实例数、图像数、目标尺度和光照分布。
    
- 将不同来源的标签统一映射，保留原始标签及转换记录。
    

交付 `dataset_v1.0`、`data.yaml`、数据划分清单、数据统计表和标注规范。

## 4.3 模型训练与算法改进

主导：A　关键协作：B　实施时间：第3—6个月

### 4.3.1 建立YOLOv8n Baseline

选择YOLOv8n作为主模型较为合理：结构相对轻量，训练和导出资料丰富，便于形成统一的速度、精度对照实验。

建议训练初始配置：

|参数|初始设置|
|---|---|
|模型|YOLOv8n预训练权重|
|输入尺寸|640×640|
|Epoch|100—150，启用早停|
|Batch size|依据GPU显存调整，初始8—16|
|优化器|使用固定版本默认配置作为起点|
|随机种子|固定并记录，最终关键实验重复3次|
|数据增强|基础几何和颜色增强，避免过度破坏裂缝纹理|
|评估指标|mAP@0.5、mAP@0.5:0.95、分类AP、Precision、Recall|

首先运行原始模型，记录训练日志和失败案例。不要在获得Baseline结果之前同时修改网络结构、损失函数与增强策略。

如果Baseline精度较低，应先检查标注质量、类别定义、数据来源和检测尺度，而非直接增加更复杂的注意力模块。

### 4.3.2 面向低光照的自适应增强

推荐以自适应Gamma校正 + CLAHE作为第一版方案。

Gamma校正用于提升较暗区域的可见性，CLAHE用于改善局部对比度。两者可以单独或组合使用，但必须通过对照实验确定收益。

建议处理流程：

1. 将输入图像统一到正确的颜色空间。
    
2. 计算亮度均值、暗像素占比等统计量。
    
3. 判断是否启动增强，避免对正常光照图像重复增强。
    
4. 对弱光图像实施带参数边界的Gamma校正。
    
5. 在亮度通道执行CLAHE，并限制对比度增强幅度。
    
6. 对增强结果进行噪声、纹理和运行时间检查。
    
7. 将模块嵌入训练及推理流程，保证两端处理一致。
    

可使用附件中提出的自适应Gamma思路：

$$\gamma = \frac{\ln L_{\mathrm{target}}} {\ln(\max(L_{\mathrm{mean}},\epsilon))}$$

其中亮度已经归一化，目标亮度和Gamma上下限由验证集确定。

初期可尝试 `clipLimit=2.0` 和 `tileGridSize=(8,8)` 的CLAHE设置，再根据效果调整。

注意：

- 弱光增强会同时放大传感器噪声和水渍纹理。
    
- 过强增强可能将混凝土纹理变成类似裂缝的伪特征。
    
- 不应仅以增强后图像更明亮作为算法有效的依据。
    
- 必须衡量增强耗时，比较精度收益与CPU成本。
    

建议增加一个专门的低光照实验矩阵：

|实验|增强方式|研究目的|
|---|---|---|
|L0|不增强|原始对照|
|L1|固定Gamma|判断基础亮度提升效果|
|L2|CLAHE|判断局部对比度增强效果|
|L3|自适应Gamma|判断动态亮度调整效果|
|L4|自适应Gamma + CLAHE|验证组合方案的综合收益|

低光照测试集应包含真实拍摄的弱光图像，合成弱光图像主要用于训练增强和辅助实验。

### 4.3.3 面向微小裂缝的模型优化

建议最多选择两项结构或训练策略作为主要研究对象，不要同时引入大量改进模块。

方向一：增加P2检测层。

原YOLOv8检测头通常主要使用较低分辨率的多个特征尺度。增加P2检测层，可以提供更高分辨率的预测特征，有望改善细小裂缝的响应。

需要同步考察：

- P2是否提高细小裂缝的AP及Recall。
    
- 参数量和FLOPs增加多少。
    
- ATC是否可以正确转换修改后的网络。
    
- 新的高分辨率特征图是否显著增加NPU执行时间。
    
- CPU端解码和NMS是否因候选框增多而变慢。
    

如果P2增加的延迟超过收益，就不能仅凭离线mAP提高而将其选为最终方案。

方向二：裂缝定位损失函数优化。

可将附件中的WIoU列为候选，与原始CIoU进行比较，但不预设其一定优于原模型。

需要注意一个重要区别：WIoU如果只用于训练阶段的框回归损失，通常不会作为推理图中的算子导出，因此不必直接把训练损失函数视为ATC部署的算子风险。真正需要检查的是修改后的推理网络结构。

对于很细、很长的裂缝，矩形检测框本身也存在表达限制。如果框级检测效果不足，可以增加一个小规模分割研究分支，而不是无限叠加框回归损失函数。

### 4.3.4 消融实验设计

建议采用两级实验，以节约GPU训练时间。

第一轮分别验证各项改进，第二轮只组合有明显收益的模块。

|实验编号|模型配置|目的|
|---|---|---|
|E0|YOLOv8n|Baseline|
|E1|YOLOv8n + 自适应增强|验证低光照改善效果|
|E2|YOLOv8n + P2检测层|验证细小目标改善效果|
|E3|YOLOv8n + WIoU|验证定位损失改进效果|
|E4|YOLOv8n + 增强 + P2|验证主要模块组合效果|
|E5（可选）|最优组合 + WIoU|验证最终联合方案|

第一轮每组先训练1次筛选方向；对保留的关键方案使用3个随机种子重复训练，报告平均值和标准差。

所有模型应使用相同的数据划分、评估代码和尽可能一致的训练预算。

最终选型采用精度—延迟双指标决策，不是简单选择mAP最高的模型：

$$M^*=\arg\max_{M \in \mathcal{F}} \operatorname{AP}(M)$$

其中 $\mathcal{F}$ 表示满足板端延迟、算子兼容性与稳定性约束的候选模型集合。

这一原则也可以成为论文的核心技术主线。

### 4.4.4 AMCT量化方案

建议以PTQ为第一选择，效果不理想时再考虑混合量化或QAT。

昇腾AMCT的ONNX量化流程会生成两个不同用途的文件：

- `*_fake_quant_model.onnx`：用于ONNX Runtime中的量化精度仿真。
    
- `*_deploy_model.onnx`：用于进一步通过ATC编译为可部署OM模型。
    

两者不能混淆，尤其不能将伪量化模型直接当作最终部署模型。

正确流程为：

```
FP32 ONNX
   │
   ├── AMCT PTQ + 代表性校准数据
   │
   ├── fake_quant_model.onnx
   │       └── ONNX Runtime量化精度预评估
   │
   └── deploy_model.onnx
           └── ATC转换
                  └── INT8/混合精度OM
                         └── 真实NPU评测
```

B应在第4个月先使用原版YOLOv8n验证一次PTQ流程，不等算法改进完成后才发现量化工具的依赖问题。

推荐量化决策规则：

|量化结果|后续措施|
|---|---|
|mAP下降≤2个百分点，裂缝Recall下降≤5个百分点|优先保留PTQ方案|
|整体精度可接受，但裂缝AP下降明显|检查检测头及浅层特征的量化敏感性|
|多类别精度下降较大|重新评估校准集和输入归一化|
|PTQ无法满足精度目标|尝试部分层回退为FP16或QAT|
|INT8速度未明显改善|检查数据传输、未量化算子及CPU后处理瓶颈|
|QAT时间或环境成本过高|保留FP16稳定交付版本，并如实记录INT8限制|

需要特别强调：QAT能够改善部分模型的量化误差，但并不保证将mAP损失控制在1%以内。 最终必须以板端真实测量为准。

### 4.4.5 AIPP与前处理优化

AIPP可用于部分可配置的图像预处理操作，但不能认为CLAHE和任意自适应Gamma算法都能直接由AIPP完成。

建议采用分阶段策略：

- 第一阶段：CPU完成全部预处理，保证计算正确。
    
- 第二阶段：在模型接口和数据格式匹配的前提下，尝试将支持的颜色转换、归一化等步骤迁移到AIPP。
    
- 第三阶段：比较迁移前后的端到端耗时及模型输出一致性。
    

AIPP接入后必须重新确认模型输入布局、颜色通道顺序和数值范围，避免出现图像正常但预测异常的问题。

同时，不建议实时视频处理默认使用batch大于1。对于单路低延迟检测，batch=1更符合项目目标。

### 4.5.2 实时视频处理

```
    ↓

    ├── SQLite存储

```

关键策略：

- 采集与NPU推理解耦。
    
- 推理队列最多保留1—2帧，积压时优先处理最新帧。

- 不在每帧中重复初始化OM模型。
    
- 对连续多帧同一病害进行事件去重，避免产生大量重复记录。
    
- 记录采集帧数、处理帧数和丢弃帧数，不能仅根据网页显示刷新率计算FPS。
    

性能测试至少分解为：

$$T_{\mathrm{total}}= T_{\mathrm{capture}}+ T_{\mathrm{enhance}}+ T_{\mathrm{preprocess}}+ T_{\mathrm{transfer}}+ T_{\mathrm{NPU}}+ T_{\mathrm{postprocess}}$$

该表达式用于分析单帧各环节耗时。使用流水线并行时，有效吞吐由各级处理能力和队列策略共同决定，不能简单将各模块FPS相加。

建议额外统计端到端P95延迟，并尝试将其控制在150 ms以内。

### 4.5.3 小裂缝的分辨率处理策略

仅把1080P视频缩放到640×640，可能让原本仅占数个像素宽的裂缝进一步丢失细节。

因此建议采用两种模式：

模式A：实时全画面检测。 对完整帧Letterbox到640×640，保证主要的实时帧率与监控连续性。

模式B：细节复核。 对疑似病害区域或定时抽样帧进行高分辨率裁剪检测，提高细小裂缝的可见性。

第二种模式不要求每帧都执行。若采用多图块滑窗，会明显增加NPU调用数量，应单独报告实际有效处理帧率。

这比单纯增加输入分辨率更容易兼顾系统实时性和细节识别能力。

### 4.5.4 病害量化方法

建议将病害量化分为两个技术等级。

|等级|输出内容|实现条件|
|---|---|---|
|基础等级（必做）|病害类别、数量、框坐标、像素面积、时间信息|检测模型输出|
|提高等级（选做）|裂缝像素长度与宽度、分割区域面积、标定后的物理尺寸|分割或细化算法 + 摄像头几何标定|

对于裂缝，较合理的量化流程是先获取像素级裂缝区域，再进行骨架提取与局部宽度计算。

对于剥落病害，检测框面积只能描述目标外接矩形，不能直接当作剥落真实面积。

在可标定的条件下，简化的尺度换算为：

\[ L_{\mathrm{mm}} = s L_{\mathrm{px}} \]

其中 \(s\) 是经过相机标定和拍摄几何校正后的尺度转换系数。对于距离变化明显、表面非平面或透视变形较大的场景，应采用更完整的几何校正方法。

若没有可靠标定，系统只显示像素尺寸或相对等级，不输出缺少依据的毫米数值。

- 根据事件ID避免重复写入。
    
- 提供基本身份验证，避免监控接口直接暴露在公网。
    
- 支持查看设备是否在线、最近推理时间和运行错误。
    

Web页面至少具备设备状态、实时检测画面、历史病害表格、病害类别统计和图片查看五项功能。

第一版采用局域网PC作为服务器即可，云服务器可在最终演示阶段根据实际需求接入。

# 五、关键风险与应对策略

建议将风险管理从“遇到问题再处理”改为“明确预警条件与回退方案”。

|风险|影响|应对措施|
|---|---|---|
|实际芯片型号与ATC配置不符|OM模型无法加载或执行|第1周根据`npu-smi info`确认型号，按实际SoC准备算子包和OM|
|CANN、AMCT、Python依赖不兼容|环境搭建耗时过长|冻结版本；优先验证官方样例；保留可用系统镜像；量化环境与训练环境分离|
|新增网络结构不支持ATC转换|改进模型无法部署|每次结构修改后立即导出ONNX并试转换，保留可工作的原版YOLOv8n|
|数据集存在重复和场景泄漏|测试精度虚高|按隧道及采集场景分组划分，使用去重检查，冻结独立测试集|
|剥落、泛碱等类别样本不足|类别AP低，泛化能力不足|提前确定采集来源，增加真实样本，报告类别覆盖情况，减少对合成图像的依赖|
|低光照增强引入噪声与伪影|假阳性增多|增强参数限幅；加入增强开关；进行真实弱光对照测试|
|细小裂缝分辨率不足|漏检率高|增加高分辨率特征层、目标尺度分析和局部裁剪复核|
|INT8量化导致裂缝精度下降|算法优化收益被抵消|使用代表性校准集、敏感层回退、必要时QAT；保留FP16交付版本|
|CPU后处理成为瓶颈|NPU较快但端到端帧率低|逐模块分析耗时，减少数据复制，优化NMS和线程调度|
|开发板过热或供电不稳|降频、推理失败或系统重启|使用符合规格的PD电源、主动散热和温度监控，进行持续压力测试|
|系统多线程出现队列积压|延迟增加、画面卡顿|有界队列、最新帧优先、明确丢帧策略、异常恢复机制|
|病害物理尺寸测量不可靠|工程结果缺乏可信度|无标定时仅报告像素指标；物理尺寸必须有校准和误差验证|
|不同隧道场景差异明显|实际应用准确率降低|增加跨隧道测试，对失败场景建立样本库并补充训练|
|算法改进收益不显著|论文创新性不足|保留负面实验，转向系统级精度—速度—量化鲁棒性研究，不人为制造改进|
|训练框架或数据授权限制|成果公开与工程转化受阻|核查数据许可和Ultralytics的AGPL/商业许可义务，维护第三方依赖清单|

其中，项目应设置三个明确的技术回退点：

第2个月末： 如量化工具尚未跑通，可以继续使用FP16 OM推进数据和系统工作，但必须明确量化专项攻关计划。

第6个月末： 如P2等结构改进无法在NPU上稳定部署，则使用原版YOLOv8n + 有效的低光照增强作为候选方案。

第7个月末： 如INT8量化不能同时满足精度和稳定性要求，则允许FP16作为主交付模型，将INT8结果作为论文的量化适配实验，而非强行交付低精度版本。

这样能够降低项目因一个技术难题而整体延期的概率。

# 八、论文与专利布局建议

## 8.1 论文研究主线

我更建议将论文的主要贡献凝练为：

面向低光照与微小裂缝场景，在昇腾边缘NPU算子及量化约束下，实现隧道衬砌多类病害检测的精度—效率协同优化。

这比简单宣称“改进YOLOv8n并部署到香橙派”更有研究价值，也更符合附件中强调的四重约束。

建议论文围绕以下三项可验证贡献展开。

### 贡献一：低光照与细小裂缝检测优化

通过自适应增强与高分辨率特征提取，比较不同模块对细小裂缝AP、召回率和低光照场景鲁棒性的影响。

重点通过消融实验说明哪项技术确实有效、作用于哪些困难样本、代价是什么。

### 贡献二：面向Ascend NPU的精度—速度协同部署

针对YOLOv8n及改进模型建立FP16、INT8或混合精度部署的对照实验。

不仅展示模型是否能转换成功，还分析不同量化方案对各病害类别精度和实际板端速度的影响。

特别强调裂缝检测对量化误差的敏感性，以及采用何种策略实现合理折中。

### 贡献三：端到端边缘系统验证

展示从摄像头采集到NPU检测、缺陷信息记录和远程查看的实际效果。

报告真实视频流帧率、平均延迟、P95延迟、CPU及内存占用、运行稳定性和低光照场景表现。

这项贡献的价值来自可复现的工程实验，而不仅是完成一个Web页面。

## 8.2 论文实验安排

|实验类型|实验内容|预期回答的问题|
|---|---|---|
|Baseline对比|原始YOLOv8n与改进方案|改进模型是否真正有效？|
|低光照对比|无增强、Gamma、CLAHE、自适应组合|哪种增强方式收益最高？|
|结构消融|原版、P2、WIoU、组合模型|哪个模块贡献最大？|
|小目标专项|不同尺寸、宽度和光照条件的裂缝|细小裂缝的主要漏检因素是什么？|
|部署精度对比|PyTorch、ONNX、FP16 OM、INT8 OM|不同部署阶段造成了多少精度变化？|
|量化实验|PTQ、敏感层回退、可选QAT|如何控制INT8精度损失？|
|性能分析|各模块延迟、CPU与NPU资源占用|实际瓶颈在哪里？|
|泛化验证|不同来源或隧道场景|模型是否过度依赖训练场景？|
|系统稳定性|连续运行、断网恢复、异常重启|原型是否具备基本工程可靠性？|

如果实验结果表明改进模型精度更高但速度较低，可以绘制精度—延迟散点图或Pareto对比图。这类结果对于边缘计算论文尤其有解释价值。

# 九、执行优先级与最终验收建议

对于这支三人团队，项目成功的关键不是实现的技术越多越好，而是保证每一个技术环节都有明确证据和可复现结果。

建议从项目开始就采用以下优先级：

|优先级|必须保证的任务|原因|
|---|---|---|
|P0|数据质量、FP16 OM基础部署、准确的模型评估|决定项目是否具有可靠技术基础|
|P1|低光照增强、小裂缝改进、INT8部署、完整边缘系统|构成项目主要研究与应用价值|
|P2|分割测量、物理尺度估计、混合量化深入调优|形成进一步技术亮点，但有额外研发风险|
|P3|多摄像头、复杂云平台、真实隧道大规模部署|不宜作为当前三人团队的硬性任务|

最终结题时建议采用四项独立验收：

1. 数据验收：数据集质量、类别覆盖、独立划分和标注规范完整。
    
2. 算法验收：Baseline与最终模型、完整消融、低光照测试及独立测试数据齐全。
    
3. 硬件与系统验收：OM模型实际运行、FP16/INT8对照、实时监控、稳定性测试和完整日志。
    
4. 科研成果验收：论文结论由实验支持，代码可复现，知识产权材料与实际完成的创新相符。
    

## 最终实施建议

结合附件原规划、昇腾工具链特性和实际团队能力，最应坚持的是三个原则：

先建立能在真实NPU上运行的基础方案，再进行算法研究。 这样算法改进始终有明确的硬件约束。

把算法精度、量化精度和系统速度作为相互关联但分别测量的指标。 避免出现离线模型很好、量化后退化、系统又无法实时运行的情况。

第9个月前完成稳定系统，第10个月以实验和科研成果为主。 最后两个月是保障成果质量的缓冲期，不应成为补做核心技术模块的时间。

按照这一安排，项目不仅能够形成一套实际运行的香橙派隧道病害检测原型，还能够积累具有学术价值的低光照检测、NPU量化部署和精度—延迟权衡实验结果。对于有导师指导、具备一定CV与嵌入式基础的三人大学生团队，这是相对稳健且具备研究深度的实施路线。
